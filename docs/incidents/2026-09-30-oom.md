# Incident 2026-09-30: out-of-memory freeze of Valhalla (7 h)

**Severity:** high. The owner's machine was unusable from 08:43 to 15:37 EDT and needed a hard reset.
**Caused by:** Claude (this project's session). **Data loss:** none found (see Damage).
**Status:** contained, causes fixed at source; one decision left for the owner (see Open).

## What happened
| Time (EDT) | Event | Evidence |
|---|---|---|
| 06:29:54 | **First OOM, missed.** The first local audit run had 16 agents in parallel; seven ngspice (2.0–2.6 GB each) and two python3 (3.4 + 2.0 GB) filled RAM. The kernel killed one ngspice and the machine recovered. **Claude did not notice.** | `journalctl -b -1 -k`: "Out of memory: Killed process 63634 (ngspice)" |
| ~06:35 | Owner stopped that audit to save usage-window budget (unrelated to memory). | session log |
| 08:35 | Claude's own cron poke fired. Claude **resumed the same audit unattended** while the owner slept, and in parallel unzipped and analysed 270 WAV files in the foreground. | crontab, session log |
| 08:43:08 | **Second OOM.** Six FreeRouting JVMs (1.7–2.3 GB each), a 1.1 GB kicad-cli and python3 processes: ~30 GB anonymous memory against 30 GB RAM + 8 GB swap. The kernel killed `claude-desktop` (Electron sets `oom_score_adj` 300, so it is the preferred victim), which freed only 630 MB. | kernel task dump |
| 08:43:10 | Last journal line. The system thrashed (page cache down to 3.4 MB) and never recovered. | `journalctl --list-boots` |
| 15:37:45 | Hard reset by the owner. | boot list |

## Root causes
1. **Unbounded parallelism.** The workflow runtime allows min(16, cores − 2) concurrent agents, which is 16 on a 32-thread CPU. The audit script set no memory budget or concurrency cap of its own.
2. **Agents launched heavy tools freely.**
   - Auditors wrote their own SPICE testbenches: ~2.3 GB per ngspice, against 450 MB for the repo's `bridge_spice.py` (measured after the incident).
   - Auditors re-ran FreeRouting, whose JVM defaults to ¼ of RAM.
   - Nothing fenced any of it.
3. **The first OOM was a warning that went unread.** Claude checked the workflow journal but never the kernel log, so it didn't learn the audit had already caused one OOM kill.
4. **Unattended escalation.** Claude built the cron poke that restarted the workload with nobody present to intervene. The owner asked for it; the design gap is Claude's.
5. **The safety net didn't hold.** The kernel OOM killer picked a low-value victim. `systemd-oomd` needs 20 s of sustained pressure above 50% and logged no action: either the freeze outran its window, or it starved too. There is no swap-based kill configured (`oomctl`: no swap-monitored cgroups).

## Damage check (after reboot)
- `git fsck` clean; working tree clean, so no tracked file was modified by auditors.
- 5 commits made that day existed only on the local disk. **Pushed to GitHub at 15:44.**
- The workflow journal (107 lines) is intact, with 10 finished audit results cached.
- Harness smoke tests: all 9 pass after the fixes.

## Fixes (all verified)
| Fix | Where | Verification |
|---|---|---|
| Cron poke disabled | `crontab -l` (line commented, reason noted) | no live `claude -p` line |
| This session fenced: MemoryHigh 14G, MemoryMax 18G, MemorySwapMax 2G | `systemctl --user set-property` on the current Konsole scope (runtime only) | kernel `memory.max` reads 19327352832 |
| Fence mechanism proven | — | a 1 GB allocation in a 256 MB fence was killed (exit 137); the machine and session were unaffected |
| Future sessions start fenced, inside tmux | `tools/claude-session.sh` (dedicated tmux socket, so it can't borrow an unfenced server) | tmux server confirmed inside the fenced cgroup |
| Audit concurrency capped at 5 live agents | `.claude/workflows/adversarial-methodology-audit.js` | syntax-checked |
| Agents must fence every sim (≤ 3–4 G) and must not run FreeRouting | same file, HARD RULES | — |
| FreeRouting heap capped at 1 GB | `tools/env.sh` (`FREEROUTING_JAVA_OPTS`), `hw/pod/place.py`, smoke test | smoke suite passes inside a 4 GB fence |

## Open (owner decision; needs sudo, so not done)
- **Belt-and-braces system setting:** a swap-based kill in `systemd-oomd` (e.g. `ManagedOOMSwap=kill` on `user.slice`), or `earlyoom` with `--avoid` for the desktop. Not done: needs a sudo password at the machine, and the per-session fence already addresses this project's cause.
- **When to re-enable the cron poke.** Recommendation: only once sessions start via `tools/claude-session.sh`, so anything it restarts is fenced.

## Lessons (process)
- **Before resuming heavy background work, read the kernel log for OOM kills,** not just the task's own journal.
- **Nothing unattended starts heavy work on a shared machine without a fence.**
- **"Works in the cloud container" is not evidence about the owner's machine.** Seventh instance of this today.
